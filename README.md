# llm-price-compare

把不同厂商、不同计价口径的大模型 API 价格，归一化成一张可比的表。

同一个模型，有人报 `$3 / 1M tokens`，有人报 `¥0.021 / 1K tokens`，有人报 `$0.0000035 / token`，还有人只给一个「5 折」。这个脚本把它们统一换算成 **元 / 百万 tokens**，并按你业务的真实用量结构算「混合成本」，再排序。

> 核心观点：比价难的不是算数，是先对齐口径。口径不对，算得再快也是错的。

---

## 快速开始

```bash
python3 price_compare.py prices.example.csv --rate 7.10 --out-share 0.3 --cache-hit 0.4
```

## CSV 格式

表头固定七列，顺序随意，缺的留空：

| 列 | 说明 |
|---|---|
| `provider` | 供应商标识，随便写 |
| `model` | 模型名 |
| `currency` | `USD` 或 `CNY` |
| `unit` | `per_token` / `per_1k` / `per_1m` |
| `input` | 输入单价（按上面的 unit 填） |
| `output` | 输出单价 |
| `cache_read` | 缓存读取单价，没有就留空 |

`cache_write` 可选，脚本不参与排序（写入是一次性成本，按命中率折算容易失真）。

示例见 [`prices.example.csv`](prices.example.csv)。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--rate` | `7.10` | 美元兑人民币汇率。**请换成当天的**，别用记忆里的数字 |
| `--out-share` | `0.30` | 输出 token 占比。对话约 0.2–0.3，写代码或长文可到 0.5+ |
| `--cache-hit` | `0.40` | 输入命中缓存的比例。固定知识库 0.5–0.8，一次性长文本接近 0 |

后两个参数不是"设置"，是**你业务的输入**。填错，排名就错。

---

## 混合成本公式

```
总成本 = 输入tokens × [(1 - cache_hit) × 输入价 + cache_hit × 缓存读价]
       + 输出tokens × 输出价
```

按 100 万 tokens 总量计算。输出价通常是输入价的 3–5 倍，所以 `--out-share` 对结果的影响比很多人想象的大。

没有填 `cache_read` 的行，按**最坏情况**处理（命中部分仍按输入价算），所以这类供应商在表里会偏贵——这是有意的保守估计。

---

## 三个使用提醒

**1. 只比同一档位的模型。** 表里混了 flash 和 pro，排名没有意义。脚本不做同档位校验，这是使用者的事。

**2. 折扣字段别读反。** 如果数据源给的是 `percent_off = 90`，那是"便宜 90%"，你付 10%，即一折。换算关系：

```
折数 = (100 - percent_off) / 10
percent_off = 50  →  5 折
percent_off = 99  →  0.1 折
```

**3. 长上下文阶梯价、图片 token 折算，脚本都处理不了。** 这两类要单独建表：阶梯价按你真实的上下文长度分布加权；图片按"每张图折算多少 token"单列。

## 关于

由 [LONG AI](https://ai.dijinlong.com/) 维护。我们做的是一个**多卖家报价**的大模型 API 平台：
同一个模型由不同卖家各自挂价，调用方按卖家报价付费，一个密钥、OpenAI 兼容。

这几个脚本最早是内部工具 —— 平台上几百个模型的计价口径要对齐，各家的「OpenAI 兼容」也要逐个验，
后来整理成能独立跑的版本放出来。

这套东西一共三个仓库，并列放在同账号下：

- `llm-price-compare` —— 把不同计价口径归一化成一张可比的表
- `llm-api-compat-check` —— OpenAI 兼容层的 5 项体检
- `llm-scheduler-demo` —— 多货源派单：健康分 + 熔断 + 带探索的加权选择
